## Problem
- Current agentic web-testing evaluations depend on **predefined checklists** (NL test cases), which can't keep up with AI-generated apps that add unanticipated features.
- They are also limited to the simple interactions found in web-generation benchmarks.
- **How well VLM agents can discover bugs on their own has not been measured systematically** (p.1–2).

## Method
- **CAT paradigm:** the agent **writes Playwright code** to drive the browser, collects textual and visual feedback, and explores on its own to find bugs (§3.1).
- Testing is framed as a **POMDP** with horizon H. A termination action returns PASS or NOT_PASS plus a list of bugs. Reward = a match score against the ground-truth bugs (§3.2).
- **CATJudge environment:**
  - Remote Docker service per app (npm install / run dev, then teardown).
  - Xvfb display shared by **Browser-Use (Playwright)** and **Computer-Use (PyAutoGUI)** tools.
  - Isolation: separate servers, or separate virtual displays.
- **Initial input:** a QA-oriented **project document** (features, tech stack, key state variables) plus a screenshot. So it is *not fully spec-free*.
- **Core tools:** Playwright script execution, accessibility tree on demand, wait, terminate. Only the latest screenshot is kept in context.

## Data
- **CATTest: 102 AI-generated web apps** across 9 usage categories (Fig. 3).
  - Generated by Claude Code with Opus 4.6 from requirement sets made progressively harder.
  - **Ground-truth bugs** were annotated by humans and AI together:
    - Humans reproduce each candidate bug.
    - Claude Code checks the source for the defect.
    - **Pooling across several tools** (as in competition benchmarks).
    - Repeated until every new report is a false positive or a duplicate (§3.3.1).
- **Metrics:**
  - **R-score:** recall of ground-truth bugs. Matching is done by Gemini-3-Flash, which agrees with humans 96–98% of the time (Table 2).
  - **P-score:** share of reported bugs that are real.
  - Pass/not-pass classification metrics as well.

## Results
- Settings (p.7): H = 250 turns, temperature 1.0.
- **Main results** (Table 1):

  | Model | R-score | P-score | Note |
  |---|---|---|---|
  | **Claude-Opus-4.7** | **42.57** (best) | 38.30 | n/a |
  | Gemini-3.1-Pro | n/a | **48.56** (best) | n/a |
  | GPT-5.5 | 39.41 | 46.88 | n/a |
  | Qwen3.6-27B | 33.56 | n/a | Best open model |
  | GPT-5.4 | 17.58 | n/a | Pass/fail recall 93.67 |
  | Qwen3.5-9B | 14.71 | n/a | n/a |

  - **No model finds even half the ground-truth bugs while keeping its reports trustworthy.**
  - Models are good at saying "something is wrong" (pass/fail recall up to 98.65) but bad at naming the specific bug. GPT-5.4 shows this most sharply: pass/fail recall 93.67 but an R-score of only 17.58.
- **Workflow ablation** (Table 3):

  | Mode | R-score | P-score |
  |---|---|---|
  | **Hybrid** (Playwright) | 42.57 | 38.30 |
  | User-side (PyAutoGUI only) | 32.94 | n/a |
  | **Developer-side** (static code review, no browser) | 35.87 | **10.60** |

  - Without runtime evidence, the model "**massively over-reports speculative defects**".
- Strong models prefer writing scripts over atomic actions, which also means fewer tool calls (Fig. 5).

## Limitations

**Stated by the authors (p.9):**
- The ground-truth bug set is incomplete, so the R-score doesn't penalize extra reports.
- Models report trivial "bugs".
- Only functional correctness is covered (no accessibility or UX).

**Spotted myself:**
- **Dataset**
  - **AI-generated, mostly front-end apps**, unlike long-lived human-written CRUD apps with back-ends and databases.
  - The bug distribution reflects Claude-Code mistakes.
- **Method**
  - It gets a QA project document, which is a light spec.
  - Single agent.
  - No coverage measurement and no state model.
  - **No verification step:** reported bugs are matched as they come, and replay isn't used to filter them.
- **Evaluation**
  - Temperature 1.0, and the paper doesn't say how many runs were done or report variance.
  - Cost per app is only in the appendix.
  - The LLM matcher could be biased toward wordings similar to its own.
- **Generalizability:** whether results carry over to classic multi-page server-rendered apps is unknown.

**Future directions:** bigger ground-truth bug sets; subjective quality dimensions; better tools for weaker models.

## Relevance to our project
- **Held-out benchmark for G3 and generalization:** 102 Dockerized apps with ground-truth bugs and an automatic R/P scorer. We can run a subset (e.g. 20 apps) as an external test that was never seen during development.
- **G2 evidence:**
  - P-scores of at most 48.6 for frontier models mean **more than half of the reported bugs are wrong**.
  - Static review without execution reaches only P = 10.6.
  - So execution evidence is decisive, which supports our replay-based gate.
- **Design ideas:**
  - The finding that agents writing Playwright scripts beat atomic clicks argues for a script-execution tool in our workers.
  - The per-episode Docker deploy/teardown is the reset mechanism our evidence gate needs.
- **Metric to borrow:** the R-score/P-score pair is exactly the recall/precision framing we use for G2.
